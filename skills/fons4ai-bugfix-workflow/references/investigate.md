# 复杂缺陷调查

先收集可复现输入、环境、版本、错误表现与正确预期，区分事实和假设。用最小复现验证假设，按调用链缩小范围，不先做大规模重构。

涉及组件包时检查真实版本和配置；线上数据或服务操作遵守实际授权，默认使用隔离复现。无法复现时记录已有证据与缺口，不能把推测写成根因。

确认原因后采用最小修复，保留能够防止复发的测试；关键数据/安全问题需要对应边界验证。需求预期变化按 [重新规划与转接](../../fons4ai-sdd-plan/references/replanning.md) 处理，先判断基线与复杂度，不混在缺陷修复里。

只有跨会话调查、多人协作或用户要求时，在 `docs/development/bugfixes/` 写一份简短记录：症状与预期、原因证据、修复、实际验证、遗留问题。无需固定长报告、证据等级和所有可能章节。
