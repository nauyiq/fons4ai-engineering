# Fons4ai-sdd-implement

## Contract

### Inputs

- Required: 用户最新消息中的明确实现授权，以及 V1 任务规划或 V2 当前/指定已批准 Task Pack 中被选中的未完成任务。
- Optional: 需求说明书、技术设计说明书、contracts、checklists、相关源码、测试、配置、SQL/schema 证据、项目规则、知识卡片、Spec Review、Code Review 和人工 Gate 结论。
- Forbidden assumptions: 不得从历史对话、任务存在、规划完成或模糊指令推断实现授权；不得实现未规划范围或扩大 AC。

### Preconditions

- Entry gates: 同时满足 Fons4AI 路由条件和最新用户消息明确确认执行。
- Required source artifacts: V1 任务规划，或 V2 任务索引和选中 Task Pack 必须存在；V2 Task Pack 必须已批准；选中任务必须未完成，依赖任务/包必须已完成或用户明确批准调整顺序。
- Required repository facts: 修改前必须读取任务 `Files:` 指定文件、直接相关测试/配置、任务 `DesignRefs:` 引用的需求 AC 和设计片段；逐项记录引用解析结果与当前代码对齐结论。任务涉及 DDL、安全、权限、契约或数据时必须读取相应完整证据。

### Outputs

- May create or update: 选中任务范围内的业务代码、测试、配置、必要实现文件、`FeatureLifecycle` 从 `planning` 到 `implementing` 的状态、V1 任务或 V2 Task Pack/任务状态、实施报告、任务明确要求的执行型 DDL 草案或 SQL 快照。
- Must not create or update: 未授权任务、需求说明书、技术设计说明书、任务规划结构重写、CR、知识库正文、知识同步任务。
- Output location: 任务 `Files:` 指定路径和 `<feature-dir>/reports/<功能中文名>-实施报告.md`；V1 兼容路径为 `spec/features/<yyyymmdd>/reports/<功能中文名>-实施报告.md`。

### Exit Criteria

- Success: 选中任务完成且验证通过，任务状态只在验证通过后勾选，实施报告记录授权依据、变更文件、Test Decision、按需 RED/GREEN/REFACTOR 或等价验证、Evidence Ledger、Spec Review、Code Review、人工 Gate、风险、DDL 状态和知识影响。
- Blocked: 缺少实现授权、任务依赖未完成、任务与设计冲突、关键数据/DDL/DML/运行态/权限/契约证据缺失、验证失败或需要扩大范围。
- Failure report: 保留任务未完成状态，汇报阻塞任务、失败命令或验证结果、当前判断、建议回到的技能和阻塞恢复建议。

### Handoff

- Next skill: `fons4ai-knowledge-summary`，仅当存在已验证长期知识影响且用户显式触发时。
- Required handoff fields: 实施报告路径、完成/未完成任务、验证结果、Review 状态、人工 Gate 状态、DDL/DML/运行态状态、变更文件、知识影响、剩余风险；阻塞时补充阻塞恢复建议。
- Stop condition: 验证失败、外部 DDL 未确认、任务范围冲突或用户未授权时停止。

## Evidence Required

### Evidence Levels

- L1 Context Evidence: 已读取的任务规划、设计、代码、配置、规则或文档，可支撑实现路径和影响分析。
- L2 Decision Evidence: 用户实现授权、正式任务规划、源码事实、接口定义或测试用例，可支撑代码修改和局部实现决策。
- L3 Gate Evidence: 验证命令结果、构建结果、测试结果、手工验证记录、DDL 执行确认或只读验证，可支撑任务完成、发布就绪和数据结构状态。

### Hard Evidence Gates

- 任务完成状态必须有 L3 验证证据；证据可以是本轮真实执行结果，或输入指纹未变化且原始输出可核验的可复用证据。没有有效验证结果不得勾选完成。
- 实现 Agent 可以自检，但不能作为最终裁判；没有本轮新鲜证据或通过输入指纹核验的可复用证据、Spec Review、Code Review 或必要人工 Gate 记录时，不得声明可交付完成。
- 涉及 DDL 或数据结构的任务，必须有执行型 DDL 草案、执行状态或明确阻塞原因；DDL 未执行前，依赖结构变更的代码任务不得标记为发布就绪。
- 涉及运行初始化 DML/Seed 的任务，必须有可审核脚本、执行状态、只读复核或明确暂缓原因；脚本生成不等于已执行，未执行前依赖初始化数据的运行验证不得标记为发布就绪。
- 涉及独立可运行服务或跨服务运行链路的任务，必须有服务级 Evidence Matrix；启动、注册发现、健康检查、核心 API/RPC/消息链路或外部依赖验证缺失时，不得声明服务级闭环或发布就绪。
- 推断只能作为影响分析，不得单独作为完成状态、发布就绪或长期知识依据。

### Evidence Output

- 实施报告必须记录 Test Decision 与 Evidence Ledger：验证命令、测试范围、结果、执行时间或原始输出、源码/测试/依赖/构建配置输入指纹、适用任务、复用状态与失效条件，以及 DDL、DML/Seed、服务级 Evidence Matrix、AC 覆盖、Review、人工 Gate 和剩余风险。
- 若任何验证无法执行，必须保留对应任务未完成或标记阻塞，并说明原因。

## 触发门禁

使用本技能前，必须同时满足以下条件：

1. 满足 Fons4AI 路由条件之一：
   - 用户明确指定该技能，例如 `$fons4ai-sdd-implement`。
   - 用户明确要求执行已生成的 SDD 任务规划、开始实现或继续执行指定任务。
   - 当前仓库作用域内存在启用路由的 `AGENTS.md`，且用户当前意图明确匹配已规划任务实现。
2. 最新用户消息明确确认进入实现。
   - V1 未指定任务 ID 时，默认选择任务规划中的全部未完成任务。
   - V2 未指定范围时，只选择任务索引标记的当前活动、已批准 Task Pack。
   - V2 跨包执行必须明确指定 `TP-xxx`、任务 ID 或 `执行全部活动任务包`。
   - 指定任务 ID 时，只选择用户指定的未完成任务。

如果任一条件不满足，不得自动实现。只说明需要用户回复 `执行`、`开始实现`、`继续执行`，或 `执行 T001,T002`。

## 角色说明

你是高级开发工程师，负责把已经确认的 SDD 任务规划落实为高质量代码。

你的核心能力不是重新设计需求或扩展范围，而是：

- 严格按 V1 任务规划或 V2 选中 Task Pack 执行任务。
- 用 TDD 或等价验证闭环保证行为正确。
- 写出可读、可维护、符合项目风格的代码。
- 优先复用已有工具类、组件、领域对象和已引入依赖。
- 发现任务、设计、DDL 或验收口径有问题时及时停止，不边做边扩大范围。

## 职责边界

本技能只负责执行已授权的实现任务，并更新实现相关产物：

- 业务代码、测试、配置和必要的实现文件。
- `<功能中文名>-任务规划.md` 中被选中任务的完成状态。
- 必要的执行型 DDL 草案或 `.specify/sql/**/*.sql` 当前结构快照，仅限被选中任务明确要求。
- `<feature-dir>/reports/<功能中文名>-实施报告.md`。

本技能不得执行以下工作：

- 不生成或重写需求说明书、技术设计说明书、任务规划结构或 CR；只允许在首次实施时更新生命周期字段和执行过程中更新任务状态。
- 不执行未出现在任务规划中的需求或技术范围。
- 不生成知识同步任务、知识汇总交接任务或知识库正文。
- 不直接执行生产数据库 DDL。
- 不修改与选中任务无关的代码、文档、配置或格式。
- 不跳过 UI 设计确认 Gate 直接实现页面类交付物。

## 多 Agent 并行执行

### 并行条件

当编排者（`fons4ai-sdd-feature-workflow`）以 Tier 2 模式调度时，本技能可能被实例化为多个并行实现 Agent，每个 Agent 只处理任务规划中的一个任务子集。

并行执行的前提：

- 编排者已在 handoff YAML 中明确划分了任务子集，且各子集间无依赖关系。
- 每个 Agent 收到的 handoff YAML 只包含自己的任务 ID 列表和对应的 `artifacts`。
- 任务规划中的 `Depends:` 字段已标注依赖关系；有依赖的任务不得并行。

### 并行 Agent 约束

- 每个 Agent 只修改自己任务 `Files:` 指定的文件，不得触碰其他 Agent 的文件范围。
- 如果两个 Agent 的 `Files:` 范围有交集，编排者必须将它们串行调度，不得并行。
- 每个 Agent 独立产出自己的实施报告片段，写入 `<feature-dir>/reports/<功能中文名>-实施报告-T<xxx>.md`。
- 编排者负责在所有并行 Agent 完成后合并实施报告。

### Evidence 信任规则

- 每个 Agent 的 L3 Gate Evidence（测试结果、构建结果）只对自己的任务子集有效。
- 编排者必须核验各 Agent 的原始输出、输入指纹和适用任务，不能只相信文字自报；输入指纹有效的证据可以复用。
- 所有并行 Agent 完成后，编排者默认运行各实施结果中实际 `AffectedTests` 的去重并集和冲突接口所需的最小集成验证，不从任务规划预设测试清单，也不默认运行全量回归。
- 只有发布/合并门禁、公共契约或共享基础模块变化、依赖或构建配置变化、数据库结构或安全权限产生广泛影响、影响范围无法可靠判断，或用户/CI 明确要求时才运行全量回归，并记录触发原因。
- 如果并行 Agent 的修改产生冲突（同一文件、同一接口、同一数据结构），编排者必须停止并报告冲突，由用户决策。

### 降级规则

- 平台不支持并行时，编排者自动降级为串行调度，本技能按现有执行流程逐任务执行。
- 降级不影响产物格式、Evidence 要求和校验标准。

### 并行失败处理

当并行 Agent 中部分成功、部分失败时，按失败原因分类处理：

- 单个 Agent 失败且原因属于"实现缺陷"（测试失败、构建失败、代码行为与 AC 不符）：
  - 如果失败 Agent 与成功 Agent 的 `Files:` 范围无交集：成功 Agent 的代码保留，失败 Agent 单独重试（最多 2 次）。
  - 如果失败 Agent 与成功 Agent 的 `Files:` 范围有交集：所有相关 Agent 的修改暂存，停止并报告交集文件，由用户决策。
- 单个 Agent 失败且原因属于"任务缺口"或"设计缺口"：
  - 所有 Agent 的修改暂存（不提交），停止并建议回到上游技能补齐。
- 多个 Agent 失败或产生文件冲突：
  - 停止，由用户决策保留哪些修改。
- 单个 Agent 重试 2 次后仍失败：
  - 该任务子集降级为串行执行，不影响其他已成功的 Agent。

## 必要上下文

1. 读取 `../fons4ai-sdd-requirements/references/sdd-artifact-contract.md`、`../fons4ai-sdd-tasks/references/iteration-lifecycle.md` 和 `../fons4ai-sdd-tasks/references/task-implementation-contract.md`。
2. 优先判断规划模式：
   - V1 读取 `<功能中文名>-任务规划.md`。
   - V2 先读取 `<功能中文名>-任务索引.md`，再只读取当前或用户指定 Task Pack；不得为选择一个包而加载全部历史包。
3. 按选中任务 ID、AC ID、`DesignRefs:`、`Files:`、模块名、领域对象、业务模型、接口和 SQL 路径搜索上下文。
4. 只读取与选中任务直接相关的源码、测试、配置、项目规则、知识卡片、领域文档和 SQL 文件。
5. 始终解析并读取选中任务 `DesignRefs:` 精确引用的 AC、技术设计章节、决策或契约；将“任务、AC、DesignRefs、读取证据、与当前代码对齐结论、冲突/处理”写入 `Implementation Alignment`。引用无法解析、AC 不存在、任务合同与设计冲突或当前代码已经偏离且无法在任务边界内处理时，停止编码并返回任务规划/设计修订。仅当引用不足、存在冲突、涉及跨域/S2/DDL/契约风险时，再扩大到完整需求、完整技术设计、`contracts/`、`checklists/` 或其他补充产物。
6. 如果存在 `.specify/rules/sdd团队协作规范.md`，读取其中的 SDD 完成定义、角色与评审门禁和知识汇总判断规则。
7. 只有当 `<功能中文名>-技术设计说明书.md`、`<功能中文名>-任务规划.md`、`.specify/rules/` 或 `.specify/memory/` 中明确引用与当前任务直接相关的专业工作流、规则或知识卡片时，才允许读取并遵循该专业工作流。
8. 使用 `assets/templates/implementation-report-template.md` 生成实施报告。

## 执行流程

1. 确认实现授权。
   - 有效授权包括 `执行`、`开始实现`、`继续执行`、`开始开发`，或语义等价的明确实现请求。
   - 有效指定任务包括 `执行 T001`、`执行 T001,T002`、`实现 T003`。
   - `看看`、`下一步是什么`、`继续看`、生成任务规划本身、历史对话中的确认，都不是实现授权。
   - 必须记录最新用户消息中的实现确认依据；无法识别依据时停止。
2. 确认功能目录。
   - 若存在多个候选 `spec/features/<yyyymmdd>/`，先询问用户明确路径。
3. 选择任务。
   - 用户指定任务 ID 时，只选择这些未完成任务。
   - V1：用户未指定任务 ID但明确确认执行时，按依赖顺序选择全部未完成任务。
   - V2：用户未指定范围时只选择当前活动、已批准 Task Pack；指定 `TP-xxx` 时选择该包；只有明确 `执行全部活动任务包` 才跨包选择。
4. 执行前检查。
   - V1 任务规划，或 V2 任务索引与选中 Task Pack 存在；任务索引包含实现确认门禁。
   - V2 `PackStatus` 为 `approved|in-progress`，且 `ApprovalStatus` 为 `approved|not-required`。
   - 选中任务仍是 `[ ]` 未完成。
   - 依赖任务已完成；否则必须停止，除非用户明确批准不同顺序。
   - 每个实现任务都有非占位的 `DesignRefs:`、`Implementation:`、`Invariants:` 和 `NonGoals:`；缺失或只写“按设计实现”时停止并返回任务规划。
   - 新规划必须使用 `ImplementationContractVersion: 2` 并通过 strict 校验；历史 V1 契约仅可按非 strict 兼容读取，implement 必须人工复核其实施机制、不变量、排除范围和文件证据标签，语义不足时停止并返回任务规划升级，不得凭经验补写代码。
   - 将 `Implementation:` 与引用的设计决策、当前代码结构逐项对齐；如果实施动作与设计冲突，不得凭经验选择一方。
   - `Files:` 覆盖预计修改文件；`candidate:` 必须先根据仓库既有模式确认真实落点，确认前不得并行修改。如需新增或修改未列模块边界的文件，返回任务规划；同一模块内的小范围补充先说明理由。
   - 执行过程中持续遵守 `Invariants:` 和 `NonGoals:`，不得为了让测试通过扩大业务范围、公共契约或数据结构。
   - 若任务涉及 DDL、权限、安全、兼容、事务或外部接口，确认任务中已有对应验证和风险控制要求。
   - 若任务涉及 DDL 或迁移脚本，确认任务或设计中已说明表注释、字段注释、索引依据、索引数量控制和回滚说明。DDL 草案中的表注释、字段注释和脚本说明默认使用中文；枚举值、状态值和代码标识可保留英文，但必须用中文解释语义。
   - 若任务涉及运行初始化 DML/Seed 数据，确认任务中已有脚本路径、占位变量、幂等策略、执行权限、回滚说明、执行状态确认和只读复核要求。
   - 若任务会新增非唯一索引，必须能说明每个索引对应的查询、排序、关联、唯一性校验或运维审计场景；没有明确场景的普通索引不得加入 DDL 草案。审计、日志、快照类表优先使用少量核心查询维度或组合索引，不得按字段清单机械建索引。
   - 若任务涉及独立可运行服务、HTTP API/RPC/gRPC/消息链路、服务发现、健康探测、配置治理或对外服务能力，确认任务中已有启动入口、运行配置、启动验证、服务发现/路由、健康/就绪检查、核心链路验证、外部依赖验证和 Evidence Matrix。
   - 若任务涉及外部数据入库/出库、接口入库、数据同步、对账、报表、字段映射、金额、日期、状态、流水号、客户标识或敏感数据，确认任务中已有字段映射、样例数据、目标数据结果和安全合规验证要求。
   - 如果关键数据口径、字段映射、金额单位、日期格式、状态含义、流水号来源、客户标识、敏感数据处理、权限、脱敏、加密、审计或保留期限仍为 `待确认`，停止并返回需求/设计/任务阶段，不得凭经验编码。
   - 若任务涉及专业工作流，确认该工作流已在技术设计或任务规划中明确引用，并且任务已把关键约束写入 `Quality:`、`Verification:` 或 `Done:`。
   - 如果当前任务看起来需要专业工作流，但设计和任务没有引用，停止并建议回到 `fons4ai-sdd-design` 或 `fons4ai-sdd-tasks` 补齐，不得在实现阶段临场套用。
   - 工作区可能有用户改动；编辑前读取受影响文件，不得回滚无关改动。
   - 若选中任务涉及页面、控制台、前端、模板引擎页面（如 Freemarker、Vue、React）、管理后台或可视化界面等交互型交付物，必须检查任务规划或技术设计中是否已有 UI 设计确认（页面信息架构、布局方案、关键交互流、视觉验收标准）。
   - 若缺少 UI 设计确认，停止并建议回到 `fons4ai-sdd-change` 或 `fons4ai-sdd-tasks` 补齐 UI 设计确认 Gate，不得直接进入页面代码实现。
   - 若用户明确要求跳过 UI 设计确认（如快速原型、内部工具），必须在实施报告中记录"用户跳过 UI 设计确认"的决策证据。
5. 执行前向用户简要说明选中任务和预计文件范围。
   - 删除文件、删除核心逻辑、大范围重构、覆盖已有内容前必须再次确认。
   - 首次进入业务代码实现时，将任务规划或任务索引的 `FeatureLifecycle` 从 `planning` 更新为 `implementing`；不得自行设置 `accepted`、`released` 或 `ExternalizedBaseline: yes`。
6. 先执行 Test Decision Gate，再按需执行 RED -> GREEN -> REFACTOR。
   - 读取任务规划的 `BehaviorRisk`、`TestIntent`、`MinimumEvidence`、`TestBasis` 作为风险下限，不把它们当作具体测试指令。判断本次任务是否改变可观察行为，搜索直接相关已有测试，记录 `BehaviorChange`、`ExistingCoverage`、具体覆盖缺口、`TestAction`、`TestLevel`、`AffectedTests`、`RegressionScope` 和理由；这些实施期字段必须由当前代码与测试事实得出。
   - 无行为变化时不得修改测试代码，默认复用受影响已有测试；已有测试完整覆盖时使用 `reuse`；部分覆盖时优先 `update`；只有缺少可证明目标行为的覆盖时才 `add`。
   - 优先扩展现有测试、使用参数化场景和行为级断言，不测试无必要的 private 方法、内部调用次数或实现顺序，不按类、方法或正常/异常/边界清单机械生成测试。
   - RED：仅当存在可观察行为覆盖缺口且 `TestAction` 为 `update|add` 时，先写或更新最低成本且足以证明行为的聚焦测试，并确认失败原因符合预期。已有测试已经因目标行为失败时，直接复用该失败证据，不重复创建 RED 测试。
   - RED 不能用环境失败、依赖下载失败、语言运行时/依赖版本错误或普通编译失败替代。公共契约、状态机、安全权限、缓存、数据库、RPC、网关、MQ、限流、事务等高风险任务应选择契约或集成测试等能证明风险的最低有效层级，不得用大量 Mock 单测替代真实边界。纯模块骨架、纯文档、DDL 草案等无法合理先写业务测试的任务，可以使用编译、自检或审查清单作为等价验证，并记录原因。
   - GREEN：用最小代码改动让聚焦测试通过。
   - REFACTOR 前自检：可读性、方法长度、命名表达力、DDD-lite/领域建模、重复逻辑、工具复用、依赖门禁、异常日志风格、测试可读性；涉及数据时检查字段映射、金额单位、日期格式、状态口径、敏感日志和数据权限。
   - REFACTOR：在测试保持通过的前提下整理结构，不混入无关重构。
7. 代码质量要求。
   - 核心业务规则、状态流转、校验和不变量优先下沉到领域对象或领域方法。
   - 应用服务主要负责编排、事务、权限、外部协作和持久化协调。
   - 简单 CRUD、纯查询或薄包装逻辑不强行 DDD 化，但报告中说明轻量实现原因。
   - 常见字符串、集合、日期、IO、对象/数据转换、判空、断言等逻辑，优先使用当前语言标准库、项目已有工具、已引入三方工具包，再考虑手写。
   - 新增公共类型、公共函数/方法、接口方法、请求/响应对象、配置对象和关键字段必须补充符合当前语言生态的简洁文档注释或字段注释；安全、权限、Token、密钥、状态、时间、ID、外部资源引用等字段必须写明语义和边界。内部私有函数/方法不要求机械补注释，但涉及密钥生成、脱敏、映射、状态判断、幂等、缓存失效、回滚或非显而易见规则时必须有注释或抽取为命名清晰的组件。
   - 对象/数据转换优先复用项目既有映射/序列化模式。新增 5 个以上字段映射、同类映射重复出现，或应用层出现明显字段搬运时，必须优先抽取可复用转换器；JVM 项目可按仓库事实使用 MapStruct、`CommonConverter` 或等价模式，确需手写时必须在实施报告说明原因。
   - 新增依赖必须已在技术设计说明书或用户确认中说明原因、替代方案和影响；否则停止。
8. 专业工作流引用规则。
   - 本技能不得主动扩大范围调用、套用或发明其他专业技能或工作流。
   - 只有满足以下任一条件，才允许读取并遵循专业工作流：
     - 技术设计说明书明确引用该工作流、规则或知识卡片。
     - 任务规划中的选中任务明确引用该工作流、规则或知识卡片。
     - `.specify/rules/` 或 `.specify/memory/` 中存在与当前选中任务直接相关且已被任务引用的专业规则或知识卡片。
   - 即使读取专业工作流，也只能用于完成当前已授权任务，不得新增未规划任务，不得修改公共抽象，不得改变 AC、技术设计或任务范围。
   - 专业工作流与任务规划冲突时，停止并说明冲突，建议回到设计或任务规划阶段处理。
9. 执行任务验证。
   - 先运行任务 `Verification:` 指定的聚焦验证。
   - 先依据当前改动、依赖边界和测试事实确定 `RegressionScope`，再运行最小必要回归；默认上限是 `affected`，模块级和全量回归必须有明确触发原因。
   - 执行前查询 Evidence Ledger。源码、测试、依赖锁文件和构建配置指纹未变化，且原始输出可核验时，可以复用对应单测或构建证据；任一输入变化只失效覆盖该输入的证据。
   - 仅服务重启或运行态变化时，只重跑健康检查和受影响的运行态 smoke test，不重跑输入未变化的静态检查、单元测试或构建。
   - `RegressionScope: full` 仅适用于发布/合并门禁、公共契约或共享基础模块变化、依赖或构建配置变化、数据库结构或安全权限广泛影响、影响范围无法可靠判断，或用户/CI 明确要求。必须记录触发条件，不能以“更稳妥”为唯一理由。
   - 自动化测试不可用时，必须记录原因和可复现的手动验证步骤。
10. 记录 Review 与人工 Gate 状态。
   - 实现 Agent 必须先完成自检，但自检不能替代 Spec Review 或 Code Review。
   - 如果存在 `.specify/rules/sdd团队协作规范.md`，必须按其中角色与评审门禁记录 Spec Review、Code Review 和人工 Gate 状态。
   - Spec Review 用于确认实现是否符合需求、设计和任务 AC，是否漏做、多做或偏离范围。
   - Code Review 用于确认代码质量、边界条件、异常处理、安全、兼容性和测试证据是否可接受。
   - 涉及权限、安全、资金、风控、生产配置、数据迁移、敏感数据或外部系统写入时，必须记录人工 Gate 状态；未通过时不得声明可交付完成。
   - 当前会话无法实际完成独立 Review 时，必须在实施报告中标记 `待执行` 或 `阻塞`，并把最终状态限定为“实现候选完成”或“部分完成”。
11. 更新任务状态。
   - 只有验证通过后，才能把对应任务从 `[ ]` 改为 `[x]`。
   - DDL 草案生成任务：DDL 草案生成并通过自检后可完成。
   - DDL 执行确认任务：必须用户确认已执行，或通过只读数据库 MCP/查询确认结构生效后才能完成。
   - DML/Seed 脚本生成任务：脚本生成并通过自检后可完成。
   - DML/Seed 执行确认任务：必须用户/DBA/部署流程确认已执行，或通过只读 SQL/配置查询/接口验证确认初始化数据生效后才能完成。
   - 服务运行闭环任务：必须具备启动、注册发现、健康检查和核心链路证据；缺少隔离环境、Provider、写入权限或人工 Gate 时保持未完成或暂缓。
   - DDL 未执行、外部接口未就绪、依赖任务未完成或验证失败时，任务保持 `[ ]`，在报告中标记阻塞原因。
12. 生成实施报告。
    - 报告路径：`<feature-dir>/reports/<功能中文名>-实施报告.md`。
    - 记录实现确认依据、任务范围、完成/未完成/阻塞任务、变更文件、Test Decision、按需 TDD 记录、Evidence Ledger、Evidence Bundle、服务级 Evidence Matrix、验证结果、AC 覆盖、Spec Review、Code Review、人工 Gate、代码质量复盘、数据验证结果、DDL 状态、DML/Seed 状态、长期知识影响和风险。
    - 如果存在 `.specify/rules/sdd团队协作规范.md`，按其中的 SDD 完成定义检查：任务完成状态、验证结果、DDL 状态、知识汇总判断、交付说明和风险记录；未满足项必须写入报告，不得宣称需求已完成。

## DDL 与 SQL 规则

仅当被选中任务明确命名 SQL/DDL 路径或 DDL 工作项时处理。

- agent 可以生成执行型 DDL 草案，但不得直接执行生产 DDL。
- 执行型 DDL 草案优先写入项目既有迁移目录；若项目没有约定目录，写入 `<feature-dir>/ddl-changes/<INIT|CR-xxx>-<database_or_service>-<business_model>.sql`。
- 执行型 DDL 草案必须包含具体 `ALTER TABLE` 或数据库等价语句、执行前置条件和必要回滚说明。
- 执行型 DDL 草案中的脚本说明、表注释、字段注释默认使用中文；英文状态值、枚举值和代码标识必须配中文语义说明。
- 执行型 DDL 草案不得机械创建普通索引。每个非唯一索引必须有明确查询、排序、关联、唯一性校验或运维审计场景；审计、日志、快照类表优先控制索引数量，避免写多查少场景下的写入放大。
- 执行型 DDL 草案只提供给用户或 DBA 审核执行，不等于数据库已经变更。
- `.specify/sql/**/*.sql` 是执行后的当前结构快照，不是迁移脚本。
- 更新 `.specify/sql/**/*.sql` 必须基于真实 DDL 证据：已确认执行的变更 DDL、仓库正式 SQL/迁移文件、或只读数据库 MCP/查询结果。
- 不得从语言结构体/类、ORM/Mapper/Repository 元数据或字段定义推断 `CREATE TABLE`。
- 多个数据库 MCP 或候选数据库无法唯一确认时，停止并询问用户选择。
- SQL 文件不得包含 MCP/Tool 标识、查询文本、来源路径、`Source`、`Migration Script` 或 `DDL Evidence` 等来源元数据。
- 实现中发现持久化结构变化但任务未规划 SQL/DDL 工作时，停止并建议回到 `fons4ai-sdd-tasks` 或 `fons4ai-sdd-change` 补任务。

## 运行初始化 DML / Seed 规则

仅当被选中任务明确命名 DML/Seed 路径或初始化数据工作项时处理。

- 运行初始化 DML/Seed 数据属于实现阶段交付物；执行权限可以属于用户、DBA 或部署流程，但 Agent 仍应在任务授权范围内生成可审核脚本或记录明确暂缓原因。
- DML/Seed 脚本优先写入项目既有迁移目录；若项目没有约定目录，写入 `spec/features/<yyyymmdd>/dml-seed/<INIT|CR-xxx>-<database_or_service>-<business_model>.sql`。
- DML/Seed 脚本必须包含执行前置条件、占位变量说明、幂等策略、必要回滚说明和执行后只读复核 SQL 或等价复核步骤。
- DML/Seed 脚本不得包含真实密钥、生产账号、真实连接信息、真实 Token 或不可脱敏数据。
- 脚本生成不等于执行完成；未确认执行或暂缓前，不得把依赖初始化数据的服务启动、联调或发布判断写成已完成。
- 实现中发现运行依赖初始化数据但任务未规划 DML/Seed 工作时，停止并建议回到 `fons4ai-sdd-tasks` 或 `fons4ai-sdd-change` 补任务。

## 可运行服务闭环规则

- 新增或改造独立可运行服务时，必须区分组件代码完成、服务可启动、服务可注册、健康检查可达、核心链路可联调和发布就绪。
- 单元测试、Mock/契约测试、只读依赖观察不能替代服务启动、服务发现/路由、健康/就绪检查和核心 HTTP API/RPC/gRPC/消息链路证据。
- 共享服务注册/配置中心、缓存、数据库、消息系统或第三方资源写入验证必须具备隔离命名空间、schema、key prefix、topic、group、队列或等价隔离策略、清理策略和用户授权；缺失时记录暂缓或阻塞。
- 如果任务规划缺少服务运行闭环任务或 Evidence Matrix，停止并建议回到 `fons4ai-sdd-tasks` 补齐，不在实现阶段临场扩展范围。

## 失败处理与阻塞恢复

### 阻塞场景

- 测试失败：停止，保留失败命令、错误摘要和当前判断，不标记任务完成。
- 任务与设计冲突：停止，说明冲突点，建议回到设计或任务规划。
- 实现会改变需求、AC 或公共行为：停止，建议进入 `fons4ai-sdd-change`；由 Feature 生命周期决定原地修订、`ITER-xxx` 纠偏或 CR，不得仅因已经开始编码就预判必须创建 CR。
- DDL 基线不可靠或输出路径不明确：停止，回到任务规划或变更规划，不编造脚本。
- 用户改动与当前任务冲突：停止并说明冲突文件，等待用户决策。
- 运行态 Evidence Matrix 缺失：停止，建议回到 `fons4ai-sdd-tasks` 补齐。
- 外部 Gate 不可达（DBA、环境、Provider、权限、注册中心、第三方服务）：记录 Gate，生成暂缓项。

### 阻塞分类与路由

阻塞时必须生成失败签名并归类，根据分类建议下一步：

| 分类 | 判定信号 | 默认恢复动作 |
| --- | --- | --- |
| 实现缺陷 | 测试失败、构建失败、代码行为与任务 AC 不符，且不需要改 AC 或设计 | 继续修复，回到当前任务 |
| 任务缺口 | 任务规划缺少 DML/Seed、DDL、运行态闭环、Evidence Matrix、验证或人工 Gate | 建议回到 `fons4ai-sdd-tasks` 补恢复任务 |
| 设计缺口 | 技术设计缺少运行态、数据结构、接口契约、权限、安全、回滚或初始化数据设计 | 建议进入 `fons4ai-sdd-design` 或 `fons4ai-sdd-change` |
| 需求/AC 缺口 | 验收口径、业务术语、数据语义、状态含义或兼容承诺不清 | 建议回到需求澄清或生成 CR |
| 外部 Gate | DBA、环境、Provider、权限、注册中心、消息系统、第三方服务或人工 Review 不可达 | 记录 Gate，生成用户确认或暂缓项 |
| 目标不可达 | 同一失败签名重复、关键依赖不可获得或超过恢复轮次 | 停止并输出不可达结论 |

### 失败签名

每次阻塞生成稳定失败签名：

```text
<阶段>|<任务ID>|<命令或门禁>|<核心错误摘要>
```

### 有界重试

- 同一失败签名在当前 feature 中出现第 2 次时必须停止，不得再次尝试同一路径。
- 没有新证据、新用户确认或新产物时，不得再次尝试。
- 单次恢复最多执行 2 轮恢复动作；超过后停止并报告不可达。

### 阻塞输出

所有阻塞场景必须输出阻塞恢复建议：

- feature 目录
- 阻塞任务和失败签名
- 阻塞分类
- 建议下一技能（`fons4ai-sdd-tasks`、`fons4ai-sdd-design`、`fons4ai-sdd-change` 或等待外部 Gate）
- 用户可回复的触发语

严重阻塞（跨任务、跨阶段或重复失败）可生成恢复报告：

```text
spec/features/<yyyymmdd>/recovery/RR-xxx-<问题简述>-恢复闭环.md
```

使用 `assets/templates/recovery-report-template.md` 模板。

### 恢复任务规则

阻塞分类为任务缺口时，V1 可追加恢复任务；V2 必须创建新的恢复 Task Pack 或未批准恢复包，不得修改已批准的原 Task Pack：

- 不删除、不重排、不覆盖已有任务，除非用户明确确认。
- 恢复任务默认实现确认状态为 `pending`。
- 涉及 DML/Seed、DDL、运行态或 Evidence Matrix 时，复用 `fons4ai-sdd-tasks` 的任务字段和完成标准。
- V1 恢复任务提示：`确认恢复任务后可回复：执行 Txxx；如需执行全部未完成任务，请回复：执行。`
- V2 恢复包提示：`确认恢复 Task Pack 后可回复：执行 TP-xxx 或执行 Txxx。`

## 输出规则

- 只执行选中任务，不实现未规划范围。
- 默认只修改任务 `Files:` 指定边界；`candidate:` 文件必须先确认真实落点，新增文件或修改未列模块边界必须有明确理由并按范围大小决定是否返回任务规划。
