# 任务角色：精简任务，不省略执行约束

先核实设计是否足以约束实现；关键契约、状态或数据决策未定时回到设计，不把“编码时再决定”当任务实施要点。按可独立验证的行为切片组织，不按每个文件、方法或 TDD 动作拆任务；测试与实现属于同一切片。

需要落盘时使用 [任务模板](../assets/templates/tasks.md)，按 [产物约定](artifact-contract.md) 引用实际依据。每个任务保留：

- 目标与依据：可观察交付目标、对应 AC/已确认行为和设计章节。
- 范围与边界：受影响模块、必要的已核实入口及不能改变的不变量；不强制穷举文件，未知路径不能写为已核实。
- 实施要点：为达到目标需要完成的关键动作与产物，引用设计结论而不重写整套方案。简单任务可以一句话，复杂任务不能只有标题和模块名。
- 验证与完成：前提、动作、可观察结果和证据；正常与关键异常都需覆盖，区分编译、实现和验收状态。

存在实际阻塞时必须写依赖和解除条件，如上游契约定稿、框架产物可消费、人工迁移生效或用户重启；无依赖不填空字段。手工验证也需明确步骤和预期，不用“后续核对”作完成标准。

任务可以用简表导航，复杂项在同一文件展开必要内容。通过设计章节链接减少重复，不恢复 13 字段、Task Pack、交接 YAML、每任务通用质量表或独立实施报告。只补任务时使用真实依据，不强制新建前置文件。

核对本次 AC/行为覆盖、依赖顺序和完成条件后，执行 [规划完整性检查](planning-review.md)，统一展示三份文档。正式工作的 [实施授权](approval.md) 集中记录在本任务文件，不逐任务审批，也不将文档生成当作授权。
