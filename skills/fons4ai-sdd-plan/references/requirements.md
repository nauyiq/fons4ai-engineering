# 需求角色：先检查就绪，再决定是否提问

完整规划必须经过本角色。用户讲得详细、提供方案或认可总体思路，都不代替就绪检查；事实充分时无需提问。先读已有资料和相关现状，区分用户决定、项目事实与 Agent 假设，不把待确认内容写成已确认。

## 就绪检查

| 维度 | 需要明确的结论 |
| --- | --- |
| 目标与价值 | 为谁解决什么问题，当前缺口与可观察结果 |
| 参与者与场景 | 谁触发、谁使用或受影响，主要使用条件 |
| 范围与非范围 | 本次包含、明确延期及必须保持的现有行为 |
| 核心流程 | 触发、主要步骤、结果，重要分支 |
| 规则与边界 | 允许/禁止条件、状态、失败、取消、重复操作等适用行为 |
| 业务数据口径 | 含义、来源、单位、归属、唯一性、未知/空/零的区别等适用口径 |
| 验收与约束 | 可核对的场景结果，以及权限、兼容、外部协作与验证限制 |

只记录本次相关结论，不强制为每项创建表格或写“不适用”。就绪检查关注业务语义，技术实现细节由设计解决。

## 澄清与探索

- 只有初步想法时，先给出基于现状的简短业务草图：用户、主场景、候选边界和假设；存在实质不同方向时给出可比较选项。草图不是正式需求。
- 先自行核实仓库能回答的问题，再集中询问影响范围、业务含义、数据口径或验收的关键分歧；不强制一轮一个问题或固定问题数。
- 阻塞问题未解决，不将依赖这些答案的设计或任务标为就绪，也不靠自行选择业务规则来凑齐三份文件。可以继续不受影响的调查；用户要求先看草案时明确标为草案与阻塞点，不进入实现。
- 非阻塞缺口说明假设、影响与后续核实条件，不把所有小问题升级为用户确认。回答足够时即停止提问。

## 输出与进入设计

使用 [需求模板](../assets/templates/requirements.md) 保留目标/范围、场景与流程、业务规则与数据口径、AC、必要约束及就绪结论。记录结论及来源，不搬问答日志。需求以业务行为为主；接口名可作定位，但字段清单和存储方案应放设计。

AC 使用稳定编号及具体前提、动作、可观察结果，覆盖适用的成功、异常和边界。计数、汇总、去重、状态转换等关键规则提供能判对错的例子，不用“准确”“正常”“最终有效”等词代替口径。

阻塞语义关闭后进入 [设计角色](design.md)，不单独要求一次阶段批准。用户只要求澄清时交付该阶段即可。需求就绪是分析结论，不等于用户批准实施。
