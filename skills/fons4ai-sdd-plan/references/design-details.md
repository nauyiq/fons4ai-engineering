# 按变化选择的设计详项

仅由设计角色在相关变化触发时读取。输出留在技术设计的对应章节，不另建全套表单。已存在且适用的详细契约直接链接并说明本次差异；没有变化的内容不复制。

## 业务流程、异步与状态

- 明确触发、输入、主要步骤、输出以及影响正确性的失败、取消、暂停、恢复分支。
- 将关键规则映射到实际模块/对象、数据依赖、事务边界和扩展点；描述不可破坏的不变量，不只列组件名称。
- 多参与方、异步执行或异常收尾：给出关键时序图，标明调用/事件、完成判定、快照/持久化时机与责任方。正常与关键异常可分图，避免一图过密。
- 状态变化：用状态表或状态图说明原状态、事件、前置条件、目标状态、失败处理。并发/重复回调涉及去重键、同步方式、幂等更新和过期结果处理时，必须说明采用的规则。
- 关键归并、统计或判断用伪代码或输入输出例子说清楚。区分一次调用、一次尝试、一次业务运行；不能仅用“最终”“有效”“去重”代替算法与身份口径。

## 接口、消息和结果契约

- 列出新增/变化的 API、事件、DTO、框架结果或 JSON 结构：生产者、消费者、入口/标识、关键字段类型、含义、必填/空值、错误及版本兼容。
- 提供足以约束实现的结构表或样例；示例值标明是示意，未核实的 API 标为候选。特别明确各类 ID 的来源、关联及去重用途。
- 说明调用/回调失败、超时、重复、未知值或缺失字段时的可观察行为；适用时明确鉴权、幂等和重试边界。不默认追踪所有外部请求或增加代理层。

## 数据结构、映射与持久化

- 分开写当前已证实结构和目标结构。当前库结构依据实际 schema、迁移文件或按授权只读核查结果，说明是否已在环境生效；ORM/类字段只能定位对象，不能证明实际 DDL。
- 新增/修改的字段给出类型、含义、可空/默认、适用索引与约束、来源/写入方；JSON 内容也属于契约，不能只写一个 JSON 列名。
- 跨步骤/系统/表映射列明来源、目标、转换/汇总/去重规则、空/未知/零语义与来源证据。业务口径仍有歧义先澄清。
- 说明事务边界、重复保存、部分失败、取消收尾及读写一致性。多表协作视需要用关系图，单字段变化不强制 ER 图。
- 明确历史兼容、迁移/回填或不回填、执行责任、部署先后、回退及生效核验；设计可写目标结构或非执行示意，不把设计交付变成实际数据库操作。运行所需初始化数据只在实际需要时展开。
- 敏感数据按实际风险说明采集最小化、访问、展示/日志处理及保留/删除；不凭空增加合规架构。

## 前端和交互

明确页面与 API 的关联方式，加载、空、未知、失败与权限状态，以及刷新、分页、重复事件、恢复后的展示规则。不用“只展示一次”“兼容旧数据”替代归属位置和判断条件。

## 发布与验证

跨仓库/依赖变化明确产物版本或识别方式、构建与消费关系。列出真实环境前置条件、人工步骤和解除阻塞的证据，区分代码完成、构建通过、迁移生效和行为验收。

为关键正常及异常场景写明前提、动作、预期和证据。遵守项目现有验证限制；即使不允许运行单元测试，也需设计适当的集成/契约/手工验证，不以编译代替。说明验证缺口，不擅自访问外部服务或生产资源。

通用选图与证据要求见 [图解规则](../../fons4ai-knowledge/references/diagram-guidance.md)。图与文字共同约束实现，不复制同一份详细流程到多个页面。
