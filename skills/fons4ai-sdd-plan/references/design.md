# 设计角色：将需求变成可执行的设计约束

先核实需求就绪结论与 AC；只补设计时接受真实资料或会话依据，不要求补造前置文件，但不能绕过阻塞的业务歧义。发现新语义问题时回到 [需求角色](requirements.md) 核实相关部分。

## 每份正式设计都应交代

1. 基线与范围：当前实现、目标变化、涉及的模块/仓库与保持不变的边界。给出已核实代码路径或符号、配置、契约或匹配版本资料入口，不能只写“沿用已有机制”。
2. 方案与决策：选用什么方案、为什么适合当前项目。只有存在实质取舍时记录重要替代方案及不采用原因，不为模板制造多个方案。
3. 业务落点：关键规则在哪个模块/对象处理，输入、输出、处理次序、依赖及不变量。应用编排与业务判断沿用现有工程结构，不强行新增 DDD 分层。
4. 复用与改动：哪些现有能力直接复用、扩展或修改，哪些确需新增，不能改变哪些公共行为。复杂计算、去重、映射或状态判断用简短伪代码解释，不编写生产实现。
5. 验证与风险：每个 AC 对应设计落点与可观察验证；重要限制、待决项及发布条件要明确，不能把关键决策全部推迟到编码阶段。

涉及通用能力、新封装或陌生 API，读取 [依赖核查](../../fons4ai-knowledge/references/dependency-discovery.md)。没有源码仍要核查组件；签名只能支持结构结论，不能据此确认运行语义。

## 根据变化展开详设

涉及业务流程/异步状态、公共契约、数据结构与映射、跨模块协作、UI 或部署变化时，读取 [适用详设](design-details.md) 的相关部分，落实对应输出。无需为无关类别建空章节，但命中项不能只留一句“按现有流程处理”。核对 [风险提示](risk-checks.md)，只有真实影响本次决策的风险进入设计。

使用 [设计模板](../assets/templates/design.md)。架构/流程图表达职责和分支；多参与方、异步、取消、恢复或事务收尾需要关键时序；有状态变化时说明状态与前置条件，不能用一张总体数据流图替代交互与状态设计。图必须基于事实，目标设计与已实现状态分开。

## 进入任务规划

关键契约、规则、状态和数据决策足以约束实现后进入 [任务角色](tasks.md)，无需单独索取设计批准；对会改变整体方向的阻塞取舍，提前集中澄清。未知事实可继续调查，但不能标为已确定或让依赖任务可执行。

用户只要求设计时止于设计；完整流程在三份文档完成后按 [实施授权](approval.md) 统一评审。少写重复背景，不削减业务设计与技术契约。
