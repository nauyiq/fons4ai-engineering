# 三份规划产物约定

正式完整规划目录：`docs/development/features/YYYYMMDD-slug/`。用户仅要求补充某个阶段时，只交付该阶段；下述三件套要求适用于完整正式规划，不自动扩大单阶段请求。

| 文件 | 负责的内容 |
| --- | --- |
| 需求说明书.md | 就绪结论、目标/范围、场景/流程、规则与业务口径、AC 和必要待决问题 |
| 技术设计.md | 方案与决策、业务落点与复用、适用的契约/数据/状态/时序、风险和 AC 验证 |
| 任务规划.md | 实施基线与授权、任务目标/依据/边界/实施要点、必要依赖、验证完成条件和执行结果 |

文件名统一，内容按复杂度调整。日期用于定位，slug 由任务语义生成，不要求用户确认命名。文档引用真实存在的来源，本地文件使用实际相对链接；依据在 Issue、不同目录文档或会话时保留其真实入口或已确认结论及来源说明，不编造链接。需求和任务分别使用 AC-1、T-1 这类简单稳定编号；单阶段任务可引用已确认行为，无需为了编号新建需求文档；Wiki 不需要卡片编号。

简单任务不创建这些文件；正式需求的三件套不能用一份泛化记录代替。附图、SQL 或接口样例只有在解释方案或验证时需要才附加，避免复制现有定义。

一次调用连续完成三个角色，统一交付三份文档；不要求用户分别调用三次，也不因统一交付跳过需求澄清。设计按实际风险展开，任务通过引用减少重复，不以篇幅短为合格标准。生成提示、空表与不适用章节删除；关键资料不足则保留具体阻塞，不用填空式猜测完成模板。

正式文档标明更新日期或版本，影响关键结论的变化简述原因。实施授权按 [统一规则](approval.md) 集中记录在任务规划；交付前完成 [交叉检查](planning-review.md)。

开发中的调整更新原文档，并简述原因与失效验证。已交付能力的实质新迭代建立新过程目录并引用旧基线。已完成记录不改写成未来计划。

任务完成后追加实际运行的验证、结果及未解决项；不强制单独报告。开发索引列出功能目录，Wiki 只沉淀当前长期结论。
