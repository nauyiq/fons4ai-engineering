# 三份文档的交叉检查

完整规划统一交付前、正式实施接手时使用。检查语义与可执行性，不以篇幅、标题、关键词或文件存在判定通过；不生成独立检查报告。

1. 需求：目标、场景、边界、关键规则与口径明确，AC 能判对错；阻塞问题已关闭，假设没有冒充用户决定。只补某阶段则核实相应真实依据。
2. 设计：每项 AC 有具体设计落点；当前事实、目标方案与未核实部分分开。涉及的业务流程、契约、数据映射、状态/时序、失败处理与兼容均已展开或引用可靠定义，不能全靠“沿用现有机制”。
3. 任务：每项工作有依据、范围、实施要点、必要依赖和可观察完成标准；已有设计用链接承接，不在任务里重新发明规则。按实际阻塞排序，明确人工迁移、重启等前置条件。
4. 验证：关键成功/异常场景有前提、动作、预期和证据；构建成功不等于验收。受项目限制无法运行的验证如实标出，不规划无权限操作。
5. 一致性：三份文档的字段口径、ID、状态、范围、非目标与验证一致；已有用户方案中仍有效的设计不能在落盘时无故丢失。重要设计只出现于聊天时，应沉淀结论或给出可用来源。
6. 可接手性：另一个 Agent 读取这三份文档及其明确引用后，能定位改动、遵守关键约束并验证结果，不必重新决定业务规则或公共契约。具体编码技巧可以留到实现，关键决策不能留空。

不满足时在对应文档补齐或记录阻塞，不将任务标为可执行。满足后统一交付，并按 [实施授权](approval.md) 判断能否进入实现；“内容就绪”和“用户批准”分别表达。
