# 代码分层与领域模型规则参考

本参考仅用于生成或更新 `.specify/rules/代码编写规范.md`。它提供可复用的职责边界，不代表所有项目天然采用 JVM、Spring、MyBatis、Apache Commons 或 DDD-lite。

## 采用门禁

只有满足以下任一条件，才把对应规则写成项目硬约束：

1. 用户明确确认架构、包结构、框架或工具优先级。
2. `AGENTS.md`、项目知识库或已有规则已明确声明。
3. 代表性源码、构建文件和测试形成一致证据，且不会与用户新决策冲突。

用户明确确认的新规则优先于框架历史代码和旧示例。除非用户要求迁移，否则规则只约束新增代码和发生实质修改的相关代码。

## 推荐职责模型

对采用分层领域模型的后端项目，优先表达为：

> 声明式入口校验 + 行为型实体 + 同域聚合根 + 领域服务决策 + 应用层业务编排 + 基础设施技术运行编排。

通用职责如下：

| 层次 | 负责 | 不负责 |
| --- | --- | --- |
| 入口层 | 协议转换、声明式结构校验、调用应用用例 | 复杂业务流程、领域状态机 |
| 应用层 | 业务用例、跨领域协作、事务、幂等、补偿和执行顺序 | 重复简单参数校验、复制领域状态机 |
| 实体 | 初始化、自身数据变化、局部判断、不变量和状态流转 | Bean 注入、持久化查询、外部调用、事务 |
| 聚合根 | 同一领域和一致性边界内的多实体协作、跨实体不变量 | 其他领域可变实体、跨领域流程、外部调用 |
| 领域服务 | 查询本领域实体、装配聚合根、复杂同域判断和持久化协调 | 其他领域数据访问、远程调用、技术运行编排 |
| 基础设施 | 框架集成、外部适配、锁/缓存/MQ/Agent/重试/调度等技术编排 | 业务状态合法性、审批结论、跨领域业务顺序 |

依赖方向必须让基础设施无法反向决定领域规则。跨领域协作传递标识、快照、上下文、结果或领域事件，不共享其他领域的可变实体。

## 包结构表达

具体包名以项目事实为准。用户确认采用横向技术分层时，可生成以下结构的项目化版本：

```text
<base-package>
├─ controller
├─ application
├─ common
│  ├─ constants
│  ├─ model
│  ├─ request
│  ├─ response
│  ├─ dto
│  ├─ vo
│  └─ util
├─ domain
│  ├─ entity
│  ├─ mapper
│  └─ service
└─ infrastructure
```

`common` 的子目录表达语义，不做机械绝对限制：内部跨层结构优先 `model`，HTTP 输入优先 `request`，HTTP 输出优先 `response`，复杂传输或集成对象可用 `dto`，页面视图可用 `vo`，稳定状态和类型放 `constants`。

## 声明式校验边界

外部入口应在进入应用层前完成请求结构校验，包括 HTTP、RPC、MQ、任务和事件消费。校验职责分三类：

| 校验类型 | 承载位置 |
| --- | --- |
| 必填、判空、长度、格式、范围、集合数量、嵌套结构 | Request 约束和入口适配器 |
| 依赖数据库、权限、幂等、外部状态的业务前置条件 | 应用层或领域服务 |
| 实体不变量、聚合一致性、状态能否流转 | 实体或聚合根 |

应用层不得重复注解已经覆盖的简单参数校验。纯请求结构的跨字段规则可以使用类级校验器；需要查询、权限上下文或远程调用的规则不得做成普通参数注解。

创建、修改、查询语义明显不同时，优先拆分独立 Request；字段和约束高度一致时才使用校验分组。Request 不兼任 Response、领域实体或持久化对象。

JVM/Spring 项目已确认 Jakarta Validation 后，才写入 `@Valid`、`@Validated`、级联校验和 Bean Validator 等具体规则。

## 领域对象边界

项目确认采用行为型实体时：

- 实体可以初始化、恢复、自校验、变更自身数据、判断局部规则和执行状态流转。
- 实体不知道数据从哪里来、如何持久化，不注入 Bean，不调用数据库、缓存、MQ、Agent 或远程服务。
- 聚合根管理同一领域、同一一致性边界内的实体，通过实体行为协调状态，不绕过实体直接改字段。
- 聚合根不得因流程复杂而无限扩大，不包含其他领域的可变实体。
- 领域服务可以使用本领域数据访问能力，装配聚合根并调用其行为；不得直接访问其他领域数据访问对象。

实体命名、聚合根后缀只在用户或项目已有规则确认后写入。例如用户确认时，可约束实体不使用 `Entity` 后缀、聚合根统一使用 `Aggregate` 后缀。

## 持久化复杂度选择

- 简单实体可以按项目约定携带最小 ORM/映射注解，但映射只表达表和字段，不能把查询构造、事务或基础设施调用带入实体。
- 复杂聚合由领域服务查询实体、装配聚合根、调用领域行为并保存发生变化的实体；聚合根不要求直接映射单表。
- 不强制所有项目完全分离领域对象与持久化对象，也不允许 Request、Response 或 DTO 直接作为持久化实体。

## 工具类规则

无 Bean 注入、无外部资源、无业务状态的纯工具放公共 util 包。依赖 Spring Bean、配置中心、数据库、Redis、MQ、文件系统、远程接口或领域状态的能力属于基础设施或领域能力，不属于 util。

工具优先级必须来自项目事实。JVM 项目已确认 Apache Commons 为常见操作首选时，可写：

1. 字符串使用 `StringUtils`。
2. 集合使用 `CollectionUtils`。
3. Map 使用 `MapUtils`。
4. 数组使用 `ArrayUtils`。
5. 项目已有框架工具优先于新增平行能力。
6. Hutool 等保留用于项目已有的日期、转换、缓存、JSON 等专项场景。

不得为单次简单调用强行引入依赖，同一模块同类能力不得无理由混用多套工具。

## 生成前检查

写入项目规则前逐项确认：

- 哪些内容来自用户决定，哪些来自仓库事实。
- 项目是否真的采用分层领域模型。
- 具体包结构、类命名和后缀是否已确认。
- 声明式校验框架及其入口触发方式是否已确认。
- Domain Service 是否允许访问本领域 Mapper/Repository。
- 简单实体是否允许最小持久化映射。
- 工具库是否已经存在于依赖中。
- 规则是否错误扩大为存量代码迁移。
