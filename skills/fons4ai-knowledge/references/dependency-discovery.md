# 依赖能力发现与核实

当设计/实现涉及通用技术能力、准备新增公共封装或依赖、或使用尚未核实的 API 时读取本文件。无需用户点名框架。范围限于本次能力，不解析整个依赖树。

## 检查顺序

1. 查相关工程约定、目标模块已有封装、调用、配置和测试。已有用法只证明其覆盖的场景。
2. 确认实际解析的组件身份、版本、作用域及本地位置。BOM 声明不等于模块引入，引入不等于运行启用；考虑锁文件、目标环境、传递依赖和版本冲突。
3. 读取对应版本文档、随包示例/声明/元数据。没有源码时继续检查组件包，不能据此认定能力不存在。按生态只加载一份：[JVM](languages/jvm.md)、[JS/TS](languages/javascript.md)、[Python](languages/python.md)、[.NET/原生组件](languages/binary.md)。
4. 先定位候选，再检查公开接口和必要配置。对本次关键语义，使用同版本文档、源码/字节码证据或针对真实组件的隔离测试核实；必要时局部反编译，不全量导出。
5. 能力适用则复用；需要适配时走已有扩展点；确认不满足时说明缺口后新增。证据不足则指出具体未决事实，继续无关工作，不能猜 API 或以自研掩盖未知。

## 证据边界

| 证据 | 支持的结论 | 不能直接推出 |
| --- | --- | --- |
| 包清单、类名、导出名 | 存在候选入口 | 适用场景、行为保证 |
| 当前版本公开签名 | 可调用接口与类型 | 时间单位、空值、隔离、一致性、重试语义 |
| 编译/类型检查 | 当前环境类型兼容 | 运行配置和业务语义正确 |
| 实际组件测试 | 测试场景下的行为 | 所有部署与所有输入均正确 |

按名称猜测的方法不能进入代码或“已验证”Wiki。不要用 Mock 的自定义行为证明第三方行为。静态检查默认不加载或执行包中的代码；只有验证需要时，在项目允许的隔离测试环境中运行，避免生产资源与副作用。

## 避免重复成本

使用 [框架接入模板](../assets/templates/framework-usage.md) 将已核实的常用入口、适用模块、关键边界及证据写入相关 Wiki 专题；无需每次单独报告。无关 API 不收录。

版本与组件指纹不变时可复用已覆盖场景的结论；版本、包内容、配置或调用场景变化时重新核实相应部分。脚本 [inspect_artifact.py](../scripts/inspect_artifact.py) 只读 ZIP 类组件清单并计算指纹，不执行、不解压、不判断语义；输出有限，未命中不证明能力不存在。

组件或工具不可获取时明确缺失的具体依据；如果该事实阻止正确实现，集中询问或请求可用资料。不要泛泛要求用户解释整个框架，也不要把缺少访问权限当作无能力。
