# README 与 Wiki 专题的图解选择

在编写或修改涉及结构关系、流程分支、交互顺序、状态或数据关系的内容时读取。简单结论、规则清单、参数或 API 对照用文字、列表或表格即可，不要求每页有图，也不要求每个专题凑齐三种图。

## 先确定阅读问题

| 读者需要理解的问题 | 优先表达 | 核实依据 |
| --- | --- | --- |
| 有哪些部分，职责与依赖边界在哪里 | 架构图（flowchart） | 模块、入口、实际依赖、配置和职责 |
| 从触发到结果如何推进，有哪些业务分支 | 业务/能力流程图（flowchart） | 用例、路由、编排、分支条件与行为测试 |
| 谁先调用谁，异步、返回或失败如何处理 | 时序图（sequenceDiagram） | 实际调用链、事件机制、契约、配置与测试 |
| 对象有哪些状态，何种条件允许迁移 | 状态图（stateDiagram-v2） | 状态定义、迁移代码、约束与测试 |
| 实体怎样关联，约束和基数是什么 | 数据关系图（erDiagram） | 明确区分领域模型、ORM 映射、迁移定义或实际数据库结构的对应证据 |

仅在图能更清楚地表达关键关系时采用。不同图回答不同问题，不把同一条直线流程换几种画法重复。优先使用可随仓库维护的 Mermaid，已有合适图继续复用。

README 保留项目概览；专题图聚焦当前阅读问题的局部结构、分支或交互。复杂细节在一个专题维护，其他页面链接过去，不复制一份易过时的图。图的粒度和术语适配业务应用、框架、CLI 或技能套件的实际内容。

## 图中的事实也需要证据

- 核实组件、边、顺序、分支和约束；不能因名称相似就推断调用、自动装配、异步机制、事务边界或基数。只有组件包时，接口签名不足以证明运行交互。
- 在图旁说明适用场景、版本或配置等关键边界，并链接能支持关键关系的来源；无需给每条边建立证据卡片。
- 当前实现与未来方案分开表达。证据不足的具体关系应省略或明确标为待核实；不能把整幅猜测图作为当前事实。数据模型图不冒充实际数据库结构。
- 图解释关系，文字补充限制和例外。不要让图成为没有上下文的装饰，也不要在正文逐字重述图上每个节点。

## 随受影响事实一起维护

更新专题时，即使不新建页面，也检查该页已有图是否受本次事实变化影响。同步修正相关文字、图和来源；只调整受影响页面，跨页通过链接保持单一详细来源。图已不再帮助理解时可以简化或移除，保留其仍有效的独有信息。

检查 Mermaid 语法、图文和来源一致性；有现成渲染工具时预览。没有实际渲染则明确验证范围，不声称渲染通过。生成提示、空图和未替换占位符不得进入交付页面。
