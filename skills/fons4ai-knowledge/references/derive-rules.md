# 提炼工程约定

输出以 `docs/wiki/工程约定.md` 为主，根 AGENTS 仅保留核心原则和加载入口。不要再生成相互重复的运行规则、代码规范、协作规范。

规则依据按适用性判断：用户明确决定、已有有效规则、目标模块的一致实践及测试。历史代码可能有缺陷或已废弃；冲突先核实，不能按数量投票或自动推广一处写法。建议与现行要求明确区分。

需要调查的维度按项目选取：

- 目录与模块边界、依赖方向、已有扩展点。
- 业务抽象、命名、注释、异常、日志和错误返回。
- 现有框架能力、公共封装、工具及测试设施。
- 接口、事务、验证、权限、缓存等实际采用的约定。

每条可执行约定尽量包含“适用场景 → 推荐入口/方式 → 代表性来源 → 重要例外”。少量简单规则放同页；复杂框架用法放独立专题并链接，不建立每个方法的卡片。

涉及通用能力、新公共封装或未知 API，强制触发 [依赖核查](dependency-discovery.md)。已有适用业务封装通常优先于直接调用底层框架；没有既定约定时选语义正确、维护成本最低的方式，不硬编码标准库或某工具库的全局优先级。

例如：仅当项目确实采用对应库及约定，才推荐 StringUtils；空白、空串、null 以及判断方向不同，不能机械替换。不得根据框架名称猜测缓存、异常或权限 API。

写入前检查规则是否有事实支撑，是否不必要地要求新分层/新抽象，是否被误扩展成存量代码迁移。完成时说明实际规则变动；未决的全局取舍集中询问，不阻塞无关事实整理。
